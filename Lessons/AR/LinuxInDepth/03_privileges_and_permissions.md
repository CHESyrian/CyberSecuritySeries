# 03 — الامتيازات والصلاحيات

## مقدمة

التحكم في الوصول في Linux مبني على أفكار بسيطة قليلة تتحد في نموذج قوي: لكل ملف مالك ومجموعة، وكل عملية تعمل ببيانات اعتماد (UID/GID/مجموعات)، وبتات الصلاحيات تقرر ما يُسمح لتلك الاعتمادات بفعله. البتات الخاصة وACLs والـ capabilities وsudo توسّع النموذج لاحتياجات العالم الحقيقي.

تشرح هذه الوحدة بتات الصلاحيات الكلاسيكية، والملكية، وبتات setuid/setgid/sticky، وقوائم التحكم في الوصول، وLinux capabilities، ورفع الامتياز المتحكم به عبر sudo — كلها من منظور واعٍ بالأمن.

---

## أهداف التعلم

بنهاية هذه الوحدة ستكون قادرًا على:

- قراءة وتفسير سلسلة الصلاحيات التي يعرضها `ls -l` والوضع الثماني الذي يستخدمه `chmod`
- تغيير الملكية والصلاحيات عمدًا وبأمان
- شرح تأثير بتات setuid وsetgid وsticky
- وصف متى تكون صلاحيات Unix التقليدية غير كافية وكيف تساعد ACLs
- فهم فكرة Linux capabilities كبديل أدق من «كل شيء أو لا شيء» لـ root
- استخدام `sudo` بشكل صحيح وفحص سياسة sudo على مستوى أساسي
- تطبيق مبدأ أقل امتياز في العمل اليومي في المختبر

## المفاهيم الأساسية

### 1. نموذج الصلاحيات الكلاسيكي

لكل ملف ودليل:

- **مالك** (UID)
- **مجموعة** (GID)
- **بتات صلاحيات** لثلاث فئات من الذوات:
  - **User** (المالك)
  - **Group**
  - **Others** (الجميع غير ذلك)

لكل فئة ثلاث صلاحيات أساسية:

| الرمز | الاسم | التأثير على ملف عادي | التأثير على دليل |
|-------|-------|----------------------|------------------|
| `r` | قراءة | فتح وقراءة المحتويات | سرد مدخلات الدليل (`ls`) |
| `w` | كتابة | تعديل المحتويات / اقتطاع | إنشاء وحذف وإعادة تسمية المدخلات **داخل** الدليل |
| `x` | تنفيذ | تشغيل الملف كبرنامج/سكربت | العبور (الدخول) إلى الدليل (`cd`) |

فارق مهم للأدلة:

- صلاحية الكتابة على دليل تتحكم فيما إذا كان بإمكانك إضافة أو إزالة أسماء في ذلك الدليل، وليس فيما إذا كان بإمكانك تعديل الملفات نفسها.
- لحذف ملف تحتاج صلاحية كتابة على **الدليل الحاوي**، وليس بالضرورة على الملف.

### 2. عرض الصلاحيات

```bash
ls -l filename
ls -ld directory
stat filename
```

مثال قائمة:

```
-rwxr-xr-- 1 alice developers 4096 Sep 30 10:00 script.sh
```

تفكيك سلسلة الوضع:

| الموضع | المعنى |
|--------|--------|
| 1 | نوع الملف (`-` عادي، `d` دليل، `l` رابط رمزي، `c` جهاز محرفي، `b` كتلي، `p` FIFO، `s` مقبس) |
| 2–4 | صلاحيات المالك (rwx) |
| 5–7 | صلاحيات المجموعة (r-x) |
| 8–10 | صلاحيات الآخرين (r--) |

### 3. الترميز الثماني

كل ثلاثي rwx قيمة 3 بتات:

| الصلاحية | القيمة |
|----------|--------|
| r | 4 |
| w | 2 |
| x | 1 |

أوضاع شائعة:

| ثماني | المعنى |
|-------|--------|
| 755 | المالك rwx، المجموعة والآخرون rx (نموذجي للتنفيذيات والأدلة) |
| 644 | المالك rw، المجموعة والآخرون r (نموذجي لملفات البيانات) |
| 600 | المالك rw فقط (ملفات خاصة) |
| 700 | المالك rwx فقط (أدلة أو سكربتات خاصة) |
| 777 | الجميع كل شيء (نادرًا ما يكون مناسبًا) |

```bash
chmod 644 notes.txt
chmod 755 backup.sh
chmod u=rw,g=r,o= file.txt     # شكل رمزي
chmod u+x script.sh
chmod go-w file.txt
```

### 4. تغيير الملكية

```bash
# تغيير المالك والمجموعة
sudo chown alice:developers file.txt
sudo chown alice file.txt          # المالك فقط
sudo chown :developers file.txt    # المجموعة فقط

# تكراري (استخدم بحذر)
sudo chown -R alice:alice /home/alice/project
```

فقط root (أو عملية ذات القدرة المناسبة) يمكنه تغيير الملكية بشكل تعسفي.

### 5. بتات الصلاحيات الخاصة

ثلاث بتات إضافية تظهر في المواضع العليا للوضع:

#### Setuid (تعيين معرّف المستخدم)

- على تنفيذي: تعمل العملية بـ **effective UID** لمالك الملف، وليس المستدعي.
- مثال كلاسيكي: `/usr/bin/passwd` setuid root حتى يتمكن المستخدمون العاديون من تحديث تجزئة كلمة مرورهم.
- يُعرض كـ `s` في موضع تنفيذ المالك (`rws` بدل `rwx`).

#### Setgid (تعيين معرّف المجموعة)

- على تنفيذي: تعمل العملية بـ **effective GID** لمجموعة الملف.
- على دليل: الملفات الجديدة المنشأة داخله ترث مجموعة الدليل (بدل المجموعة الأساسية للمنشئ). مفيد جدًا لأدلة المشاريع المشتركة.

#### Sticky bit

- على دليل: فقط مالك الملف (أو root) يمكنه حذف أو إعادة تسمية الملفات داخله، حتى لو كان الدليل قابلاً للكتابة للجميع.
- مثال كلاسيكي: `/tmp` لديه sticky bit حتى لا يحذف المستخدمون ملفات بعضهم المؤقتة.
- يُعرض كـ `t` في موضع تنفيذ الآخرين.

```bash
# أمثلة فحص
ls -l /usr/bin/passwd
ls -ld /tmp
ls -ld /var/mail   # غالبًا setgid
```

### 6. قوائم التحكم في الوصول (ACLs)

صلاحيات المالك/المجموعة/الآخرين التقليدية محدودة عندما تحتاج أكثر من مجموعة واحدة أو مستخدمين محددين بوصول مختلف. تضيف POSIX ACLs مدخلات أدق.

```bash
# عرض ACLs
getfacl file.txt

# منح مستخدم محدد صلاحية قراءة
setfacl -m u:bob:r file.txt

# منح مجموعة صلاحية كتابة
setfacl -m g:auditors:w file.txt

# إزالة مدخل ACL
setfacl -x u:bob file.txt

# ACLs افتراضية على دليل (تُورَّث للملفات الجديدة)
setfacl -d -m g:developers:rw project_dir
```

عند وجود ACLs، يعرض `ls -l` علامة `+` في نهاية سلسلة الوضع.

### 7. Linux Capabilities

بدل منح عملية root كامل (UID 0)، يمكن للنواة منح مجموعة فرعية من قوى شبيهة بـ root كـ **capabilities**. أمثلة:

- `CAP_NET_BIND_SERVICE` — الربط بمنافذ أقل من 1024
- `CAP_NET_RAW` — استخدام مقابس خام (تحتاجه بعض أدوات الشبكة)
- `CAP_SYS_ADMIN` — عمليات إدارية واسعة (ما زالت قوية جدًا)
- `CAP_DAC_OVERRIDE` — تجاوز فحوصات صلاحيات الملفات

أدوات مثل `ping` أو `tcpdump` غالبًا تُثبَّت بقدرات محددة بدل setuid root كامل على الأنظمة الحديثة.

```bash
# فحص قدرات ثنائي (إن وُجدت libcap)
getcap /usr/bin/ping
getcap -r /usr/bin 2>/dev/null | head
```

### 8. sudo — رفع متحكم به

يتيح `sudo` لمستخدم مسموح تشغيل أوامر فردية كـ root (أو مستخدم آخر) وفق ملف سياسة، عادة `/etc/sudoers` وملفات تحت `/etc/sudoers.d/`.

```bash
# تشغيل أمر واحد كـ root
sudo whoami
sudo apt update          # مثال على Debian/Ubuntu

# فتح صدفة root (استخدم بحذر)
sudo -i
sudo -s

# سرد الأوامر المسموحة (يعتمد على السياسة)
sudo -l
```

أفضل الممارسات:

- فضّل قواعد أوامر محددة على صدفات root كاملة عندما يكون ذلك ممكنًا.
- استخدم `sudo -l` لفهم ما يُسمح لك بفعله.
- لا تضع سكربتات أو ثنائيات قابلة للكتابة للجميع في قاعدة sudo.
- فضّل تحرير الملفات في `/etc/sudoers.d/` بـ `visudo -f` بدل تحرير الملف الرئيسي مباشرة.

## شرح تفصيلي — ترتيب القرار (مبسّط)

عندما تحاول عملية فتح ملف، تفحص النواة تقريبًا:

1. إذا كانت العملية تملك قدرة `DAC_OVERRIDE` (أو كانت root بامتيازات تقليدية كاملة)، غالبًا يُمنح الوصول.
2. وإلا، إذا طابق UID العملية مالك الملف → استخدم بتات صلاحيات المالك.
3. وإلا إذا طابق أحد GIDs العملية مجموعة الملف (أو مدخل مجموعة ACL) → استخدم صلاحيات المجموعة / ACL.
4. وإلا → استخدم بتات صلاحيات «الآخرين» (أو مدخل ACL «other» المقابل).
5. قناع ACL ومدخلات المستخدم/المجموعة المسماة تنقّح النتيجة عند وجود ACLs.

(الخوارزمية الحقيقية أدق وتشمل فحوصات القدرات ووحدات LSM مثل SELinux/AppArmor، إلخ، لكن ما سبق هو جوهر DAC الكلاسيكي.)

## أمثلة عملية

### فحص وتغيير الصلاحيات الأساسية

```bash
touch /tmp/demo.txt
ls -l /tmp/demo.txt
chmod 600 /tmp/demo.txt
ls -l /tmp/demo.txt
chmod u+x /tmp/demo.txt
stat /tmp/demo.txt
```

### دليل مشترك مع setgid

```bash
# (كمستخدم لديه sudo)
sudo mkdir /tmp/project
sudo chgrp developers /tmp/project
sudo chmod 2775 /tmp/project    # setgid + rwxrwxr-x
ls -ld /tmp/project
# الملفات الجديدة المنشأة داخله يجب أن ترث مجموعة "developers"
```

### عرض sticky bit (مفاهيمي)

```bash
ls -ld /tmp
# يجب أن ترى 't' في نهاية الوضع، مثل drwxrwxrwt
```

### القدرات

```bash
getcap /usr/bin/ping 2>/dev/null || echo "getcap غير متاح أو لا قدرات مضبوطة"
```

### sudo

```bash
sudo -l
sudo id
sudo cat /etc/shadow | head -3     # فقط إذا سمحت سياستك بذلك
```

## أخطاء شائعة

| الخطأ | الخطر | نهج أكثر أمانًا |
|-------|-------|-----------------|
| `chmod 777` على ملفات أو أدلة | أي مستخدم يمكنه تعديل أو استبدال المحتوى | استخدم أضيق وضع ما زال يعمل (غالبًا 644 / 755 / 600 / 700) |
| تشغيل خادم ويب أو خدمة كـ root | اختراق كامل للنظام إذا اختُرقت الخدمة | حساب خدمة مخصص + قدرات أو صلاحيات دنيا |
| ثنائيات setuid كتبتها بنفسك دون تصميم حذر | ثغرة تصعيد امتياز | تجنّب برامج setuid مخصصة؛ فضّل القدرات أو sudo |
| `chmod` / `chown` تكراري على المسار الخطأ | كسر ملفات النظام أو حبس نفسك | تحقق مرتين من المسار؛ فضّل غير التكراري عندما يمكن |
| سكربتات قابلة للكتابة للجميع مشار إليها بـ sudo أو cron | أي شخص يمكنه حقن أوامر | أبقِ السكربتات غير قابلة للكتابة من الآخرين؛ تحقق من الملكية |

## أفضل الممارسات

- الافتراضي هو مبدأ أقل امتياز: امنح فقط الصلاحيات المطلوبة.
- فضّل التعاون بالمجموعة (أدلة setgid + مجموعة مشتركة) على المواقع القابلة للكتابة للجميع.
- استخدم ACLs عندما يكون النموذج الكلاسيكي خشنًا جدًا، لكن أبقِ مجموعة ACL صغيرة وموثّقة.
- فضّل قدرات الملفات على setuid root كامل عندما يحتاج ثنائي امتيازًا أو اثنين فقط.
- عامل قواعد sudo ككود: راجعها، أبقها دنيا، واستخدم `visudo`.
- في المختبرات، تدرب على «كيف تمنح» و«كيف تدقق» الصلاحيات (`find /path -perm ...`، `getfacl`، `getcap`).

## تمرين عملي

1. أنشئ ملفًا وجرّب `chmod` بالوضع الثماني والرمزي. تحقق بـ `ls -l` و`stat`.
2. افحص `/tmp` وثنائي setuid واحد على الأقل (مثل `passwd`). لاحظ البتات الخاصة.
3. أنشئ دليلًا، طبّق setgid، ولاحظ مجموعة ملف جديد يُنشأ داخله (يتطلب مجموعة ثانية تنتمي إليها، أو sudo).
4. شغّل `sudo -l` وفسّر المخرجات لحسابك.
5. (اختياري) استخدم `find` لتحديد ثنائيات setuid على النظام:  
   `find /usr -perm -4000 -type f 2>/dev/null`

---

## أسئلة المراجعة

1. ماذا تسمح صلاحية الكتابة على دليل بما لا تسمح به على ملف؟
2. كيف يُعبَّر عن الوضع `rwxr-xr--` بالثماني؟
3. ما الغرض من sticky bit على `/tmp`؟
4. عندما يعمل برنامج setuid-root، أي UID يُستخدم لفحوصات الصلاحيات — مستدعي أم root؟
5. لماذا قد يفضّل مسؤول Linux capabilities على ثنائي setuid-root كامل؟
6. ماذا تعني علامة `+` في نهاية سلسلة وضع `ls -l`؟
7. لماذا `chmod 777` فكرة سيئة تقريبًا دائمًا على نظام متعدد المستخدمين؟

---

## ملخص

- صلاحيات Unix الكلاسيكية (مالك/مجموعة/آخرون × rwx) تبقى أساس التحكم في الوصول في Linux.
- البتات الخاصة (setuid، setgid، sticky) تعدّل السلوك للتنفيذيات والأدلة.
- ACLs والـ capabilities توفران تحكمًا أدق عندما يكون النموذج الأساسي غير كافٍ.
- يوفر sudo رفع امتياز مدققًا ومدفوعًا بالسياسة.
- التطبيق المتسق لأقل امتياز من أعلى عادات القيمة التي يمكن لممارس الأمن تطويرها.
