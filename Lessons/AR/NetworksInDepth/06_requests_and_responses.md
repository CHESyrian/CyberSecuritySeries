# 06 — الطلبات والاستجابات بالتفصيل

## مقدمة

تتبع معظم بروتوكولات تطبيق الإنترنت نمط **طلب–استجابة**: يرسل العميل رسالة طلب؛ يعيد الخادم رسالة استجابة. HTTP هو المثال المهيمن وتركيز هذه الوحدة، لكن نفس الأفكار تظهر في DNS وSMTP وتصاميم API وكثير من البروتوكولات الخاصة.

فهم بنية الرسالة والطرق ورموز الحالة والترويسات مطلوب لأمن الويب وعمل API وتحليل الحركة واستكشاف الأخطاء.

---

## أهداف التعلم

- وصف بنية طلب واستجابة HTTP
- شرح طرق HTTP الشائعة ودلالاتها المقصودة
- تفسير رموز الحالة حسب الفئة (1xx–5xx)
- قراءة والتفكير في ترويسات الطلب والاستجابة المهمة
- التمييز بين HTTP/1.1 وHTTP/2 وHTTP/3 على مستوى عالٍ
- ربط سلوك الطلب/الاستجابة بضوابط الأمن (TLS، الترويسات، التسجيل)

---

## المفاهيم الأساسية

### 1. نموذج الطلب–الاستجابة العام

```
العميل                                الخادم
  |                                      |
  | -------- طلب ----------------------> |
  |                                      |
  | <------- استجابة ------------------ |
  |                                      |
```

### 2. بنية طلب HTTP (أسلوب HTTP/1.1)

```
METHOD /path?query HTTP/1.1
Host: example.com
Header-Name: value

[جسم اختياري]
```

**طرق شائعة:**

| الطريقة | آمنة؟ | متساوية القوة؟ | الاستخدام النموذجي |
|---------|-------|----------------|-------------------|
| GET | نعم | نعم | استرجاع مورد |
| HEAD | نعم | نعم | مثل GET لكن بلا جسم |
| POST | لا | لا | إرسال بيانات / إنشاء / إجراء |
| PUT | لا | نعم | استبدال مورد |
| PATCH | لا | لا | تحديث جزئي |
| DELETE | لا | نعم | إزالة مورد |
| OPTIONS | نعم | نعم | استعلام الطرق المدعومة / CORS preflight |

### 3. بنية استجابة HTTP

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1234

[الجسم]
```

**فئات رموز الحالة:**

| الفئة | المعنى | أمثلة |
|-------|--------|-------|
| 1xx | معلوماتي | 100 Continue |
| 2xx | نجاح | 200 OK، 201 Created، 204 No Content |
| 3xx | إعادة توجيه | 301 Moved Permanently، 302 Found، 304 Not Modified |
| 4xx | خطأ عميل | 400 Bad Request، 401 Unauthorized، 403 Forbidden، 404 Not Found |
| 5xx | خطأ خادم | 500 Internal Server Error، 502 Bad Gateway، 503 Service Unavailable |

### 4. ترويسات مهمة

**ترويسات الطلب (اختيار):** `Host`، `User-Agent`، `Accept`، `Authorization`، `Cookie`، `Content-Type`، `Origin`، `Referer`

**ترويسات الاستجابة (اختيار):** `Content-Type`، `Set-Cookie`، `Location`، `Cache-Control`، `Strict-Transport-Security`، `Content-Security-Policy`، `Access-Control-Allow-Origin`

### 5. HTTP/2 وHTTP/3 (مستوى عالٍ)

| الإصدار | النقل | ميزات بارزة |
|---------|-------|-------------|
| HTTP/1.1 | TCP | نصي، طلب واحد في كل مرة لكل اتصال |
| HTTP/2 | TCP | تأطير ثنائي، تعدد، ضغط ترويسات |
| HTTP/3 | QUIC (UDP) | تعدد بلا حظر رأس سطر TCP، TLS 1.3 مدمج |

---

## أمثلة عملية

```bash
curl -v https://example.com/
curl -I https://example.com/
curl -X POST -H "Content-Type: application/json" \
     -d '{"name":"lab"}' https://httpbin.org/post
curl -vL https://example.com/
```

---

## أخطاء شائعة

| الخطأ | المشكلة |
|-------|---------|
| معاملة كل 4xx كـ «خطأ مستخدم» و5xx كـ «خطأ خادم» دون سياق | الوكلاء وWAFs يمكن أن يولدوا أيًا منهما |
| تجاهل ترويسات الأمن | غياب CSP وHSTS يزيد خطر جانب العميل |
| افتراض أن GET لا يمكنه تغيير الحالة | تطبيقات سيئة التصميم تنتهك أحيانًا دلالات الطرق |
| تسجيل ترويسات Authorization أو Cookie كاملة | تسريب اعتمادات في أنظمة السجلات |

---

## أفضل الممارسات

- استخدم TLS (HTTPS) لأي بيانات غير عامة.
- فضّل الطرق متساوية القوة لإعادة المحاولة الآمنة.
- اضبط وراجع ترويسات الاستجابة المتعلقة بالأمن.
- سجّل الطريقة والمسار والحالة والتوقيت ومعرّف طلب؛ تجنّب تسجيل الأسرار.
- في المختبرات، تدرب على قراءة الطلبات/الاستجابات الخام بـ `curl -v` وأدوات المتصفح.

---

## تمرين عملي

1. أصدر طلب GET بـ `curl -v` وحدّد سطر الطلب وخمس ترويسات على الأقل وسطر الحالة وترويسات الاستجابة الرئيسية.
2. أرسل POST بجسم JSON ولاحظ `Content-Type` ورمز الحالة.
3. أثِر إعادة توجيه واسرد رموز الحالة في السلسلة.
4. قارن عنوان URL لـ HTTP بنظيره HTTPS.
5. افحص ترويسات الأمن على موقع مختار.

---

## أسئلة المراجعة

1. أي ثلاثة مكوّنات تشكّل سطر طلب HTTP؟
2. أي فئة رمز حالة تشير إلى النجاح؟ خطأ العميل؟
3. ما الفرق بين طريقة آمنة وطريقة متساوية القوة؟
4. أي ترويسة تحمل الاعتمادات في كثير من تصاميم API؟
5. لماذا يستخدم HTTP/3 بروتوكول QUIC فوق UDP بدل TCP؟

---

## ملخص

مراسلة الطلب–الاستجابة عمود فقري لتواصل الويب وAPI. تحمل طرق HTTP ورموز الحالة والترويسات معنى وظيفيًا وأمنيًا. القدرة على قراءة الرسائل الخام مهارة أساسية للمطورين والمدافعين والمحللين.
